# 继承
## 例子了解一下继承是什么
语法，访问限定符，常用public
继承方式实现栈相比于之前的组合方式实现栈，，按需实例化，依赖模版与不依赖模版，


这是 **C++ 模板 + 继承** 中最经典，也是最容易让人困惑的问题之一。

其实**并不是因为继承，而是因为模板（Template）的两阶段查找（Two-phase Lookup）**。

我一步一步给你讲。

---

# 一、先看这个代码

```cpp
template<class T>
class vector
{
public:
    void push_back(const T& x)
    {
        cout << x << endl;
    }
};

template<class T>
class stack : public vector<T>
{
public:
    void push(const T& x)
    {
        push_back(x);   // 报错
    }
};
```

很多人第一反应就是：

> stack 不是继承了 vector 吗？
>
> 为什么不能直接调用 push_back？

事实上：

**继承没有问题。**

问题出在：

> **stack 是一个模板。**

---

# 二、如果不是模板，就不会报错

例如：

```cpp
class vector
{
public:
    void push_back(int x)
    {
    }
};

class stack : public vector
{
public:
    void push(int x)
    {
        push_back(x);   // √ 可以
    }
};
```

这是完全没有问题的。

因为：

编译器一看到

```cpp
class stack : public vector
```

立刻就知道：

```
stack
    ↓
vector
```

所以：

```
push_back
```

就在基类里面。

于是直接去基类找。

所以可以写：

```cpp
push_back(x);
```

---

# 三、为什么模板不行？

来看：

```cpp
template<class T>
class stack : public vector<T>
{
};
```

这里有一个特点：

```
vector<T>
```

里面的

```
T
```

现在是多少？

不知道。

例如以后可能变成

```
stack<int>
stack<char>
stack<string>
```

编译器现在还不知道。

也就是说：

```
vector<T>
```

到底是什么类型，

**现在不知道。**

---

## 编译器第一阶段

模板编译时：

编译器先检查

```cpp
push_back(x);
```

它会问：

> push_back 在哪里？

先找：

```
stack
```

里面。

没有。

然后：

**不会去依赖模板参数的基类里面找。**

为什么？

因为：

```
vector<T>
```

还没确定。

万一以后

```
vector<int>
```

没有这个函数怎么办？

所以：

第一阶段：

```
push_back
```

找不到。

于是：

```
error C3861
```

---

# 四、为什么 `vector<T>::push_back()` 就可以？

如果写成：

```cpp
vector<T>::push_back(x);
```

你已经明确告诉编译器：

> 去这个基类里面找。

于是：

即使

```
vector<T>
```

以后才实例化，

编译器也知道：

> 好，我以后实例化的时候再去找。

因此可以通过。

所以：

```cpp
vector<T>::push_back(x);
```

没有问题。

---

# 五、实际上还有另外两种写法

这也是面试经常问的。

---

## 方法一：指定类域（老师写的）

```cpp
vector<T>::push_back(x);
```

最直接。

---

## 方法二：使用 `this->`

```cpp
this->push_back(x);
```

为什么可以？

因为：

```
this
```

的类型是：

```cpp
stack<T>*
```

而：

```
stack<T>
```

继承了：

```
vector<T>
```

因此：

```
this->
```

会告诉编译器：

> 这是成员函数。

于是：

编译器会等模板实例化以后再去找。

所以：

```cpp
this->push_back(x);
```

也是正确的。

很多 STL 源码都是这样写。

---

## 方法三：using

```cpp
template<class T>
class stack : public vector<T>
{
public:
    using vector<T>::push_back;

    void push(const T& x)
    {
        push_back(x);
    }
};
```

这也是可以的。

它的作用就是：

把基类成员引入当前类。

以后：

```cpp
push_back(x);
```

就直接能找到。

---

# 六、为什么编译器不能自己去基类找？

这是最核心的问题。

很多同学都会问：

> 既然 stack 继承 vector，
>
> 编译器为什么不去找？

答案：

因为：

```
vector<T>
```

叫做：

> **依赖基类（Dependent Base Class）**

什么意思？

它依赖模板参数。

例如：

```cpp
template<class T>
class stack : public T
{
};
```

以后：

```cpp
stack<A>
stack<B>
stack<C>
```

继承的类完全不同。

编译模板的时候：

编译器根本不知道：

```
T
```

到底是谁。

所以：

它不能提前去里面找成员。

这就是：

> **两阶段查找（Two-phase Lookup）**

第一阶段：

只查找

* 当前类
* 非依赖名字

第二阶段（实例化以后）：

再查找

* 依赖模板参数的成员

因此：

```
push_back
```

必须告诉编译器：

> 它来自依赖基类。

于是：

```cpp
this->push_back();

vector<T>::push_back();

using vector<T>::push_back;
```

这三种方式都可以。

---

# 七、建议你这样理解（最容易记）

可以把编译器想象成一个"急性子"：

看到

```cpp
push_back(x);
```

它立刻问：

> **现在**能不能找到 `push_back`？

当前类：

```
stack
```

没有。

基类：

```
vector<T>
```

里面有没有？

编译器回答：

> 我不知道，因为 `T` 还没确定。

于是直接报错。

而如果你写：

```cpp
this->push_back(x);
```

或者

```cpp
vector<T>::push_back(x);
```

你就是在告诉编译器：

> **别急，现在先记下来，这是依赖基类里的成员，等模板实例化之后再去查找。**

所以就不会报错了。

---

## 一张图理解整个过程

```text
模板定义阶段（T 未知）

stack<T>
│
├── push()
│     │
│     ├── push_back(x)
│     │      │
│     │      ├── 当前类找 ❌
│     │      ├── 基类 vector<T>？
│     │      │       T 未知，不查找 ❌
│     │      └── 报错
│
└── 如果写成：
       this->push_back(x)
       或
       vector<T>::push_back(x)
       ↓
告诉编译器：
这是依赖基类成员，等 T 确定后再查找 ✔
```

理解了这一点，后面学习 STL 源码、模板元编程以及泛型库时，遇到类似的 `this->`、`Base<T>::func()`、`using Base<T>::func;` 就都会明白它们本质上是在解决**模板继承中的依赖基类名称查找**问题。

整体理解**90%是对的**，不过有两点需要修正，我帮你逐条分析。

---

## 1、可以理解派生类里面新增了一个成员，他是基类所有成员的集合……

✅ **这个理解可以，而且非常适合初学者。**

你可以把派生类对象想象成：

```cpp
class Person
{
    ...
};

class Student : public Person
{
    int _id;
};
```

在内存里可以近似理解成：

```cpp
class Student
{
    Person _person;   // 可以理解成隐藏的一个成员（实际不是这样实现）
    int _id;
};
```

也就是说，**派生类对象可以理解为"基类对象 + 自己新增的成员"。**

所以：

* 初始化时，要先初始化这部分"Person"
* 拷贝时，要先拷贝这部分"Person"
* operator= 时，要先赋值这部分"Person"

因此：

```cpp
Student(...)
    : Person(...)   // 初始化基类部分
{}
```

```cpp
Student(const Student& s)
    : Person(s)     // 拷贝基类部分
{}
```

```cpp
Person::operator=(s);   // 赋值基类部分
```

这种理解非常好。

> 不过严格来说，它不是"新增了一个成员"，而是**对象中包含一个基类子对象（Base Subobject）**。为了方便理解，完全可以把它看成一个隐藏成员。

---

## 2、"构造向上，析构向下"

✅ **完全正确。**

这是继承最重要的规律。

```
构造：

Person()
    ↓
Student()
```

```
析构：

~Student()
    ↓
~Person()
```

一句口诀：

> **构造向上（先基类后派生类），析构向下（先派生类后基类）。**

---

## 3、operator= 需要指定作用域

✅ **完全正确。**

因为：

```cpp
class Person
{
public:
    Person& operator=(const Person&);
};

class Student : public Person
{
public:
    Student& operator=(const Student&);
};
```

这里：

```cpp
operator=
```

已经被派生类隐藏了。

所以必须写：

```cpp
Person::operator=(s);
```

否则：

```cpp
operator=(s);
```

调用的是自己，就递归了。

---

## 4、析构函数一般不用自己显示写，因为编译器会写。

**❌ 这里要稍微改一下表述。**

应该改成：

> **析构函数中一般不用自己显式调用基类析构函数，因为编译器会自动调用。**

例如：

```cpp
class Student : public Person
{
public:
    ~Student()
    {
        cout << "~Student()" << endl;
    }
};
```

你没有写：

```cpp
Person::~Person();
```

但是实际上执行的是：

```
~Student()

↓↓ 编译器自动加上 ↓↓

Person::~Person();
```

所以：

```cpp
~Student()
{
    // 清理Student自己的资源

    // 编译器自动调用
    // Person::~Person();
}
```

因此：

**不是说"析构函数不用写"。**

而是：

> **如果你自己有资源需要释放（如 `new` 出来的内存），仍然需要写析构函数；只是不用自己去调用基类析构函数，编译器会自动完成。**

---

## 我建议你把这四点整理成下面这个版本（更准确）

> **1、可以把派生类对象理解为由"基类对象 + 派生类新增成员"组成，因此初始化、拷贝构造、赋值时，都要先处理基类部分，再处理派生类部分。可以分别调用基类的构造函数、拷贝构造函数和 `operator=`。**
>
> **2、继承中，构造、拷贝构造、赋值都要先完成基类部分，再处理派生类部分；析构则相反，先析构派生类，再自动析构基类。"构造向上，析构向下" 是继承中最重要的规律。**
>
> **3、由于派生类的 `operator=` 会隐藏基类的 `operator=`，因此调用基类赋值运算符时，需要显式指定作用域：`Base::operator=(other);`。**
>
> **4、如果派生类自己定义了析构函数，不需要显式调用基类析构函数，编译器会在派生类析构函数执行结束后自动调用基类析构函数；只有派生类自己的资源需要自己释放。**

这样表述既符合老师上课的说法，也符合 C++ 的真实机制。
